# Launch crash analysis — 2026-08-24

Affected 3DSX SHA-256:
`5ec24c9cc39aeac32b23526cfd0d81a4d83467056644fbb22bb1625d26106daa`

Exact symbolication ELF SHA-256:
`56341fdc29445da068f4f54590b29eadaae6c83c92053916de82d8c18c6eff3e`

The New Nintendo 2DS XL reported an ARM11 core 0 data abort, translation-section
fault, write access, at PC `0x00100F98` with FAR `0x07FFFA28`.

Using the exact ELF, `arm-none-eabi-addr2line` resolves the PC to `ls_app_init`
at `source/app.c:56`. The instruction is the function's first instruction:

```text
00100f98 <ls_app_init>:
    push {r4, r5, r6, lr}
```

The crash screen's SP was `0x07FFFA38`; an ARM full-descending push of four
registers writes at `SP - 16`, exactly the FAR `0x07FFFA28`.

The caller disassembly showed `main` reserving approximately 34 KiB for an
automatic `LsApp` before calling `ls_app_init`. `LsApp` contains the deliberately
bounded HTTP receive/transmit buffers, but their combined size exhausted the
3DS main-thread stack. The fault was therefore the callee prologue crossing the
unmapped stack boundary, not an intentional application write to that address.

The fix changes the single application state to static storage in BSS. The
post-fix ELF reports `app_state` as a 34,296-byte local BSS symbol, and `main`
now has only its normal register-save frame. `-Wstack-usage=4096` is enabled
under `-Werror`; a future automatic stack object of the original size will fail
the cross-build.
